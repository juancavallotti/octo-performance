> **The percentiles above are bounded, not measured.** Octo's flow-duration histogram uses Prometheus's default buckets, whose lowest edge is 5.00 ms — and this flow completes well inside it, so every observation lands in the first bucket. Interpolating there yields a number that is a function of the bucket width and nothing else, so it is reported as a bound. **The mean is exact** (a counter sum over a counter count) and is the server-side latency figure to use for this scenario.

Client p95 was 0.18 ms while the runtime's mean flow duration was 0.02 ms. **That gap is queueing at the load generator, not work in the runtime** — this run shed iterations, so k6's latency includes time requests spent waiting to be issued. Two figures that used to be indistinguishable from a slow server are now separable: the runtime was fast and the offered rate was too high.
