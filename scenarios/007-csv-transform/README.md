# 007 — CSV transformation

A CSV document arrives, and leaves as typed JSON.

This is the first workload in the lab whose **format decoder is written in CEL**
rather than compiled into the runtime. Everywhere else, the bytes are turned into a
message by Go — `encoding/json` in the HTTP source — and the expressions only
reshape what is already a structure. Here the expressions do the parsing too.

That is worth measuring on its own, and it is also the reason this scenario exists:
CSV → JSON was listed in [COMPARISON.md](../../COMPARISON.md) as a workload with no
Octo equivalent. The runtime still ships no CSV parser. What changed is that CEL
gained `split`, so one can be written.

> **No published numbers yet.** The functions this scenario needs are not in a
> released runtime, so every figure quoted below is harness calibration taken
> against a source build. Results land in [`results/`](../../results/) once the
> support ships. See the [working contract](../../AGENTS.md) on the BUILD axis.

## The integration

```
POST /transform        text/csv ──▶ multi-transform ──▶ application/json
POST /transform-rich   the same parse, plus the rest of the vocabulary
```

| | |
|---|---|
| Connectors | `http` (source, `rawBody: true`) |
| Blocks | `multi-transform` |
| Knobs | `workers`, `buffer`, `pool` |
| Request | CSV, 7 columns, header row |
| Response | JSON, the same shape scenario 006 emits |
| Ladder | 9 / 753 / 7,700 records via `PAYLOAD_RECORDS` |

CSV is not JSON, so the source is configured with `rawBody: true`: the body then
arrives as `{contentType, rawData}` with the text intact instead of being rejected
by the JSON check. Everything after that is expressions.

## The decoder

```
body.rawData.trim().split("\n").transformList(i, line, i > 0, line.split(","))
```

Split into lines, drop the header by index, split each remaining line into fields.
`transformList`'s four-argument form filters and maps in one pass, so the line list
is walked once rather than filtered and then mapped. The result is a list of field
lists, which the projection then types and reshapes.

Three things about this are worth stating plainly, because they bound what the
number means:

- **It is a naive reader.** No RFC 4180 quoting: a field containing a comma or a
  newline would be mis-split. The generator emits none. A conforming reader costs
  more than this, and that cost is not measured here.
- **CSV carries no types.** `double(f[4])` is not overhead the JSON path avoids by
  being faster — it is work the JSON path never has to do at all, because the
  document arrived with its numbers already numbers.
- **There is nowhere to put an intermediate.** `double(f[4])` appears three times
  in the projection because the extension set deliberately omits `cel.bind`, so an
  expression cannot name a subexpression and reuse it. Recomputation is the only
  option available to the author.

## What the two routes separate

`/transform` parses and projects, using `split` and `transformList` and nothing
else. `/transform-rich` runs the identical parse and then puts every remaining
library to work on each record:

| Library | In the flow |
|---|---|
| strings | `lowerAscii` on the name, `split` on the region, `join`, `format` for a display label |
| lists | `distinct().sort()` over the region's parts |
| encoders | `base64.encode` of an idempotency key |
| math | `round` to cents instead of a raw multiply |
| sets | `sets.contains` for the status test |
| regex | `extract` pulling the numeric id out of `acct-00000042`, with `orValue` for the miss |
| two-var comprehensions | `transformList` in the parse step both routes share |

The gap between the two routes is the per-record price of the wider vocabulary —
the number worth knowing before reaching for it inside a loop over 7,700 records.

## Reading it against scenario 006

[006](../006-json-transform/) sends **the same records**, generated by the same
function, as JSON. Same fields, same values, same output document. The ladder here
is sized in records rather than bytes precisely so the rungs line up: CSV holds a
record in roughly half the space, so equal bytes would have meant unequal work.

Two comparisons fall out, and they are the point of the scenario:

| | |
|---|---|
| 006 `/transform` vs 007 `/transform` | decoding a format in Go against decoding it in CEL |
| 007 `/transform` vs 007 `/transform-rich` | what the rest of the vocabulary costs per record |

Both are within-target, same-host, same-record comparisons, which is the only kind
this lab treats as sound.

## Running it

```bash
task smoke SCENARIO=007-csv-transform BUILD=dev
task bench SCENARIO=007-csv-transform BUILD=dev

# The vocabulary route
ROUTE=/transform-rich task bench SCENARIO=007-csv-transform BUILD=dev

# Up the ladder
PAYLOAD_RECORDS=753 task bench SCENARIO=007-csv-transform BUILD=dev
```

`BUILD=dev` is required until the extension libraries ship. Without it the run
stops at preflight with the list of functions the release does not declare — the
scenario declares what it needs as `REQUIRES_CEL` in `scenario.env`, and the
harness asks the artifact directly rather than trusting a version string.

## Caveats specific to this scenario

- The naive reader above is the measurement. Do not read these numbers as the cost
  of CSV parsing in general; read them as the cost of *this* parse, which is the
  cheapest correct one for input this well-behaved.
- The record count is the axis, not the byte count. A rung labelled 753 here and a
  rung labelled 100 KB in 006 hold the same records but not the same bytes.
- `k6` holds the generated body in memory and re-sends it every iteration, so the
  request side is deliberately free. What is measured is the runtime's parse, not a
  document being built.
